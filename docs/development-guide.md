# 项目开发与交付指南

> 用途：为软件项目提供可直接采用的工程、体验、质量、安全和发布基线。

## 1. 使用原则

项目应根据实际需求选择实现，并遵循经过验证的方法：

- 先明确产品边界，再选择技术方案；
- 业务规则与界面、存储和平台能力解耦；
- 从第一天考虑国际化、深色模式和可访问性；
- 核心数据写入与外部集成分开处理；
- 在开发早期建立自动化检查和正式构建流程；
- 每次发布同步更新代码、产物、测试记录和文档。

涉及旧数据、旧备份、旧接口或旧配置的改动，必须先做兼容性决策，不默认扩大实现范围：

- 先说明受影响的数据格式、用户场景、迁移成本和不兼容后果；
- 明确列出“兼容”和“不兼容”的实现差异及测试影响；
- 在需求方明确选择前，不自行新增迁移、回退、兼容别名或旧格式解析；
- 需求方选择不兼容时，按新结构实现，并同步更新测试、示例数据和相关文档；
- 需求方选择兼容时，再单独设计迁移版本、失败处理和回滚方案。

## 2. 技术栈与工具

以下技术组合已经过完整开发、测试和 Android 正式构建验证。采用时应根据产品需求重新评估，并优先选择相互兼容的稳定版本。

### 2.1 基础框架

- Flutter：跨平台界面与应用框架；
- Dart：业务、状态、数据和测试代码；
- Material 3：主题、组件和响应式界面基础；
- Kotlin：Android 原生能力与平台集成；
- Java/JDK 17：Android 编译运行环境；
- Gradle Kotlin DSL：Android 构建和签名配置。

### 2.2 状态与架构

- `ChangeNotifier`：轻量应用状态；
- `ListenableBuilder`：按状态变化重建界面；
- Repository 接口：隔离业务与存储实现；
- Service 接口：隔离文件、系统和第三方能力；
- MethodChannel：Flutter 与 Android 原生代码通信。

小型项目可直接使用 Flutter 自带状态能力。状态关系复杂、模块增多或团队扩大后，可评估 Riverpod、Bloc 等方案，但不应在缺少实际需求时增加架构复杂度。

### 2.3 本地数据与安全存储

- `shared_preferences`：少量设置和轻量本地数据；
- `flutter_secure_storage`：令牌、密钥材料或验证摘要等敏感小数据；
- `path_provider`：获取应用可用文件目录；
- JSON：完整结构化数据序列化；
- CSV：面向人工编辑或跨工具交换的数据格式。

结构化数据增长后，应将 Repository 实现替换为 SQLite、Drift、Isar 等数据库方案，不建议长期把大量业务数据保存在键值存储中。

### 2.4 加密与哈希

- `cryptography`：PBKDF2、AES-GCM 等标准密码学能力；
- `crypto`：SHA-256 等哈希能力；
- `Random.secure()`：生成 salt、nonce 和其他安全随机值；
- Base64：封装二进制字段，不能作为加密手段。

密码派生推荐 PBKDF2-HMAC-SHA256 或平台支持的同等级 KDF；内容加密推荐 AES-GCM 等带认证模式。具体参数应结合设备性能和当期安全建议评估。

### 2.5 国际化与主题

- `flutter_localizations`：Flutter 官方本地化支持；
- ARB：多语言资源文件；
- `intl`：日期、数字和语言相关格式；
- `ColorScheme`：浅色、深色和品牌主题的语义色板；
- Android `values`/`values-语言代码`：原生资源本地化。

### 2.6 文件与分享

- `file_picker`：从系统文件选择器导入文件；
- `share_plus`：调用系统分享面板导出或分享内容；
- MIME 类型与扩展名：帮助系统识别文件，但不能代替内容校验。

导入时必须验证文件内容和格式版本，不能仅信任文件名、扩展名或 MIME 类型。

### 2.7 系统与原生集成

- Flutter Platform Channels：调用原生平台能力；
- 应用私有目录 JSON 文件：保存工单主数据，并通过临时文件 `rename` 原子写入；
- `SharedPreferences`：仅作为旧版本工单数据迁移来源，不再承担主存储；
- Android `RemoteViews`：构建系统桌面组件；
- Android 运行时权限：按使用场景申请平台权限；
- Android 无边框显示：适配状态栏、导航栏和系统手势区域。

如果产品不需要对应系统能力，应删除相关原生代码和权限，保持最小权限原则。

### 2.8 可选领域能力

按实际需求选用，不应作为所有项目的默认依赖：

- `flutter_local_notifications`：本地通知；
- `timezone` 与 `flutter_timezone`：时区感知的时间调度；
- `device_calendar_plus`：系统日历读写；
- `lunar`：农历换算。

### 2.9 测试与质量

- `flutter_test`：单元测试和组件测试；
- `flutter_lints`：静态规则；
- `dart format`：统一格式；
- `flutter analyze`：静态分析；
- `flutter test`：自动化测试；
- Android Release APK/AAB 构建：验证原生代码、资源、混合依赖和签名配置。

### 2.10 版本与构建建议

- Flutter、Dart、Gradle、Android Gradle Plugin、Kotlin 和 JDK 必须作为一组验证兼容性；
- 依赖升级应先查看 breaking changes，再运行全部测试和正式构建；
- 固定关键依赖版本，避免发布时意外解析到未验证版本；
- 在 CI 或固定构建环境中缓存 Flutter、Gradle 和包依赖；
- 正式产物应记录版本号、构建号、SHA-256 和签名信息。

本项目当前 Windows 构建环境的 SDK 路径如下：Flutter SDK 为 `I:\sdk\flutter`，Android SDK 为 `I:\sdk\android-sdk`，JDK 17 为 `I:\sdk\jdk17\jdk-17.0.19+10`，Gradle Wrapper 位于 `android\gradle\wrapper`。更换构建机器时，应同步更新 README、发布检查清单和本段记录。

本项目的 Release APK 是内部专业版预览包，命令必须为 `flutter build apk --release --dart-define=ENABLE_RELEASE_PRO_PREVIEW=true`，产物位于 `build/app/outputs/flutter-apk/app-release.apk`。该预览授权只在内存中生效，不保存购买记录；正式 Google Play 包必须构建 AAB，且禁止传入该参数，未购买时按免费版权限运行。Debug 仅用于明确的调试场景，需使用 `flutter build apk --debug` 显式构建。当前 Release 构建使用 Android 模板的 Debug 签名，仅适合内部安装测试；正式发布前必须配置独立签名。记录产物大小时应同时记录构建变体、预览开关和签名状态。

## 3. 项目启动阶段

### 3.1 先明确的问题

- 产品解决什么问题，不解决什么问题；
- 首发平台、商店、最低系统版本和目标用户；
- 是否离线可用，是否需要账号和云同步；
- 哪些数据属于敏感数据；
- 数据如何备份、迁移和删除；
- 哪些功能依赖系统权限或第三方服务；
- 首次发布需要达到什么测试标准。

### 3.2 最小文档集

项目开始时至少建立：

- 产品需求文档；
- 技术架构说明；
- 数据模型与迁移策略；
- 隐私与权限清单；
- 测试计划；
- 发布检查清单；
- 商店或部署资料清单；
- 版本变更记录。

## 4. 通用架构建议

推荐使用清晰的轻量分层：

```text
domain      数据模型和纯业务规则
data        本地或远程数据访问
app         状态、用例和流程编排
services    文件、网络、系统或第三方能力
ui          页面、组件和交互
l10n        国际化资源
test        单元、组件和集成测试
```

各层职责：

- 领域层不依赖界面和平台 API；
- 数据层通过接口隐藏具体存储方式；
- 应用层负责业务流程和副作用顺序；
- 服务层封装不稳定的外部能力；
- UI 只展示状态并发送用户意图。

小项目可以使用简单状态管理，但不要让页面直接读写数据库、文件或平台通道。这样后续更换存储、增加测试或迁移平台时成本更低。

## 5. 数据与副作用

### 5.1 核心数据优先

当一次操作同时涉及本地数据和外部能力时，推荐：

1. 校验输入；
2. 写入核心数据；
3. 执行外部同步或平台操作；
4. 记录外部操作结果；
5. 对失败提供重试或修复入口。

外部能力失败不应让已经成功的数据保存看起来失败，也不应悄悄吞掉需要用户处理的问题。

### 5.2 幂等与一致性

- 重复点击或重复回调不会产生重复数据；
- 旧请求、旧页面和过期事件不能覆盖新状态；
- 删除、导入和同步操作有明确的冲突策略；
- 长流程中断后可以安全重试；
- 后台和前台同时修改时有一致的顺序规则。

### 5.3 存储选择

- 少量设置可使用键值存储；
- 结构化数据、复杂查询和版本迁移应使用数据库；
- 大文件和附件使用文件存储，并在数据库保存索引；
- 敏感令牌或密钥使用平台安全存储；
- 不要把全部业务数据长期塞进一个巨大 JSON 字符串。

## 6. 国际化

国际化应在项目初期接入。新增功能必须同时检查：

- 页面、按钮、弹窗和表单提示；
- 空状态、错误状态和异常兜底；
- 文件列名、状态值和导入结果；
- 系统通知、原生组件和平台集成；
- 日期、时间、数字和列表分隔符；
- 商店说明、隐私政策和版本说明。

推荐规则：

- 不在 UI 或底层服务中硬编码用户可见文字；
- 内部枚举使用稳定值，显示时再本地化；
- 导入时兼容稳定值和明确支持的本地化值；
- 使用长英文、窄屏和大字体验证布局；
- 切换语言后刷新所有受影响的缓存和平台内容。

## 7. 主题与深色模式

### 7.1 颜色

- 使用主题色板，不直接写死白色背景或深色文字；
- 为背景、表面、边框、主文字、次要文字和状态色定义语义；
- 状态不能只依赖颜色，还应使用文字、图标或形状；
- 深色背景避免纯黑，保留合理层次和对比度；
- 原生界面和平台组件也要跟随主题。

### 7.2 常见遗漏

- 卡片和统计块；
- 日志和列表行；
- 日历与日期选择器；
- 禁用状态和次要文字；
- 输入框、弹窗和边框；
- 图片、图表和原生组件。

每套主题至少检查浅色、深色、系统跟随和动态切换。

## 8. 布局、安全区与键盘

长页面优先使用真正可滚动的布局，并为系统区域留出空间。

通用做法：

- 页面内容使用安全区；
- 长表单和详情页使用滚动容器；
- 底部内边距叠加系统底部安全区；
- 表单允许拖动收起键盘；
- 键盘弹出后当前输入框仍可见；
- 最后一个按钮能完整滚动到系统导航栏上方。

必须验证：

- 手势导航与三键导航；
- 无边框显示；
- 小屏设备；
- 横屏；
- 大字体；
- 长英文；
- 键盘打开和关闭。

## 9. 数据导入导出与安全

### 9.1 格式设计

导入导出格式应提前定义：

- 格式名称和版本；
- 必填字段与默认值；
- 日期、枚举和布尔值格式；
- 重复数据的处理策略；
- 旧版本兼容策略；
- 非法文件和部分坏数据的处理方式；
- 导入前确认与导入后统计。

完整备份和可编辑交换格式应分开设计。不要仅通过修改扩展名伪装成加密文件。

### 9.2 加密原则

- 使用经过验证的标准算法和库；
- 使用带认证的加密模式；
- 密码通过 KDF 派生密钥，并使用随机 salt；
- 每次加密使用新的随机 nonce；
- 文件包含明确格式版本；
- 错误密码与内容损坏返回安全、可理解的提示；
- 密钥、签名文件和凭据不得写入仓库或文档。

客户端访问控制不等于数据加密。若数据本身敏感，需要独立设计静态加密、密钥生命周期和恢复机制。

## 10. 平台与第三方集成

所有平台或第三方能力都应通过服务接口隔离，并考虑：

- 权限拒绝；
- 服务不可用；
- 网络超时；
- 系统版本差异；
- 重复回调；
- 冷启动与热启动入口；
- 状态变更后的主动刷新；
- 应用升级和设备重启后的恢复。

跨技术栈共享设置时，要明确键名、类型、默认值和刷新机制。不要假设另一侧会自动感知变化。

## 11. 错误处理

错误分为三类：

- 用户可修复：提供明确原因和下一步；
- 可重试的外部错误：保留核心数据并提供重试；
- 程序错误：记录必要上下文，显示不泄露内部细节的兜底提示。

避免：

- 直接向用户显示原始异常堆栈；
- 捕获所有异常后完全忽略；
- 将不同错误统一成“操作失败”而不给解决办法；
- 因次要同步失败回滚已经成功的核心数据。

## 12. 测试基线

### 12.1 自动化测试

至少覆盖：

- 核心业务规则和边界条件；
- 数据序列化、迁移和兼容；
- 控制器成功与失败流程；
- 重复操作和幂等；
- 导入导出往返与坏数据；
- 关键页面和表单校验；
- 窄屏、大字体和长文本；
- 权限拒绝与外部服务失败。

### 12.2 每次提交或发布的检查

```text
代码格式化
静态分析
全部自动化测试
目标平台正式构建
关键流程真机或真实环境回归
产物版本与校验值核对
```

测试通过数量应记录在发布文档中，但不要只关注数量；新增高风险功能必须增加对应场景。

## 13. 发布与版本管理

标准发布流程：

1. 确认本次范围和已知问题；
2. 先核对 Google Play Console 的最大 `versionCode`，再按[发布检查清单](release-checklist.md)中的登记值递增版本号和内部构建号；
3. 执行格式化、分析和测试；
4. 生成正式签名产物；
5. 记录文件大小、生成时间和 SHA-256；
6. 在内部或测试环境验证安装与升级；
7. 只在[发布检查清单](release-checklist.md)集中更新版本、产物和校验值，再同步版本说明和商店资料；
8. 再进入正式发布流程。

构建变体规则：

- 内部 Release APK：允许直接使用完整专业版功能，必须显式传入 `ENABLE_RELEASE_PRO_PREVIEW=true`；该授权不保存、不代表购买；
- 正式 Release AAB：禁止传入 `ENABLE_RELEASE_PRO_PREVIEW=true`，专业版必须通过 Google Play 购买、恢复和服务端验证；
- 发布前必须检查构建命令和最终产物，确认预览开关没有进入 AAB。

注意事项：

- 每个独立应用必须使用独立的应用标识、签名和商店记录；
- 不同应用的签名文件和密码应严格隔离；
- 正式构建环境、依赖缓存和证书应提前验证；
- 不要在发布当天首次测试正式构建；
- 保留每个正式版本的产物、哈希和版本说明；
- 发布后应用标识和签名通常不能随意修改。

## 14. 文档管理

代码完成不代表任务结束。每次发布应同步检查：

- README 中的功能、版本和构建说明；
- PRD 中的实现状态与路线图；
- 发布清单中的测试结果和产物信息；
- 商店资料中的功能介绍和版本说明；
- 隐私政策中的权限、数据和第三方服务；
- 已知问题与后续维护项。

容易出现的文档错误：

- 版本号落后；
- 测试数量落后；
- 已实现功能仍写成未来计划；
- 不同密码或权限规则混淆；
- 旧产物路径和哈希未更新；
- 商店描述与实际功能不一致。

## 16. 禁止直接复用的内容

- 品牌名称、图标和文案；
- 应用标识、签名和密钥；
- 商店记录和隐私政策地址；
- 与当前产品无关的数据键名和格式前缀；
- 与旧业务绑定的数据模型和服务；
- 未重新评估的依赖版本；
- 未经过当前需求验证的权限和平台配置。

工程纪律、设计原则、检查清单和发布流程应作为长期基线持续执行。
